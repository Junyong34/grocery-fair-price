## 기각한 안

### DB 원본 전환 + 운영 어드민 (최초 판의 02·05·06)

최초 판은 카탈로그 원본을 운영 DB로 옮기고, 인증·인가·감사 기록·편집본/공개본 분리·카탈로그 공개 버전을 갖춘 어드민을 계획했다.

기각 이유:

- 운영자가 1명이고 코드를 직접 고친다. 어드민이 줄여 줄 "개발자 개입"이 없다.
- git이 감사 기록·전후 비교·롤백을 이미 준다. DB 원본에서는 이를 다시 만들어야 하고, 무료 플랜에는 자동 백업도 없다.
- 운영자 권한 계정, CSRF, 동시 편집 충돌, 공개 버전 표는 모두 새로 만들 코드이고 실패 지점이다.

다시 볼 조건은 spec의 "이 전제를 다시 볼 조건"에 있다.

### 카탈로그 전용 공개 버전 체계 (최초 판의 06)

화면용 카탈로그 정보를 판정 payload에 실으면 기존 포인터 하나로 버전 일관성이 생긴다. 별도 버전 표는 필요 없다.

### 정기 제철 매핑 점검 작업 (최초 판의 04)

제철 데이터와 시세 카탈로그가 모두 코드에 있으므로 vitest로 검사할 수 있다. 운영 DB 상태(판정 행 유무)만 05 보고서로 본다.

## 반박해야 할 전제

### 1. 검색 결과가 늘면 찾기 어려워지는가?

최초 판은 "한 품종의 조합이 수십 개"를 반례로 들었다. 실제로는 최대 6규격, 다규격 품종 43개다. 품종 묶음 + 규격 우선 정렬이면 충분하다. 반례는 규모를 과장했다.

### 2. pending은 모두 누락된 정상 데이터인가?

아니다. 구코드·범위 밖 상품·정보 부족이 섞여 있다. 최근 관측된 것부터 보고, 오래된 구코드는 대부분 제외한다.

### 3. 연결하면 과거도 채워지는가?

관측값이 남은 기간만 채워진다(KAMIS 90일, 참가격 6 조사일, 축평원 전체). 최초 판과 1차 리뷰는 이 부분을 부정확하게 적었다.

- 최초 판: "보관 기간이 지나면 삭제된다, 조사한다"고만 썼다. 실제 기간은 마이그레이션에 이미 정해져 있다.
- 1차 리뷰: "원본은 영구 보관이고 원본에서 재계산하는 경로가 있다"고 썼다. 틀렸다. KAMIS 원본은 1년 보관이고, 원본 재파싱 경로는 재등록 처리 전용이다. 매핑 변경용 일반 재계산은 없다.

결론: 원본 재파싱 재계산은 만들지 않고, 신규 연결은 첫 집계일부터 보여 준다.

### 4. 코드 원본이면 운영 판단이 덮어써지지 않는가?

`--classes`는 코드에 없는 품종을 숨기므로, DB 손편집은 덮어써진다. 그래서 손편집을 금지한다(02). 반면 `applyMappings`는 운영자가 다르게 정한 매핑을 보존하고 알린다. 제외·보류가 다음 배치에서 pending으로 돌아오지 않는지는 출처별로 확인이 필요하다(03).

### 5. 포인터를 되돌리면 복구되는가?

공개 화면은 되돌아가지만, 다시 매핑된 관측값·일자 요약은 그대로다. 잘못된 매핑은 `git revert` + 재적용으로 고친다(06).

### 6. 1인 운영이면 백업이 덜 중요한가?

아니다. 코드 밖 운영 결정(`store_seller`, `calc_param` 등)은 지금 백업이 없다. 카탈로그 작업과 상관없이 주간 `pg_dump`를 먼저 한다.

## 1차 범위와 제외

1차: 백업, 규격별 판정·검색(꽃게·시금치 검증 후 전체), pending 보고서 + 코드 수정 흐름, 제철 명시 매핑 + 누락 테스트.

범위 밖: DB 원본 전환, 운영 어드민, 카탈로그 공개 버전, 원본 재파싱 재계산, 자동 연결·AI 분류, 규격 속성 필터, slug 변경·품종 병합, 외부 API 추가, 수집·Storage 재작성.

## 확인 전 하지 않을 작업

운영 DB 마이그레이션·카탈로그 적용·라우트 변경은 계획 확인 후 티켓 단위로 한다.

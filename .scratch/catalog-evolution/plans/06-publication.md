# 06. 공개와 복구

Status: needs-triage
의존: 다른 계획이 따르는 공통 규칙. 백업은 지금 바로 할 일.

## 결정

공개는 지금 있는 판정 묶음 + 포인터(`judgment_current`) 교체로 한다. `judgment/cli.ts`는 새 묶음을 쓰고, 검사를 통과하면 포인터를 바꾸고, 화면은 뷰 `current_judgment`만 읽는다. 카탈로그 편집본·공개본을 따로 두는 버전 체계는 만들지 않는다.

## 버전 일관성: 화면용 카탈로그 정보를 판정 묶음에 싣는다

검색·상세·제철 링크가 서로 다른 시점의 카탈로그를 보지 않게, 화면이 쓰는 카탈로그 정보를 판정 payload에 함께 넣는다.

- 규격 slug·이름·기본 여부(01)
- 제철 ID 목록(04)
- 품종 이름·별칭(지금 별도 캐시로 읽는다면 payload로 옮길지 구현 때 판단)

이렇게 하면 포인터 하나가 공개 상태 전체를 정한다. ADR 0004("payload는 화면 모양")와도 맞는다. 카탈로그를 코드에서 바꿔도 다음 판정 묶음이 나오기 전까지 화면은 바뀌지 않는다.

## 배포 호환 (ADR 0004 보완)

ADR 0004는 "옛 모양을 읽는 소비자가 없다"고 보고 웹과 배치를 함께 바꾼다. 규격 필드 추가는 배포 시점이 엇갈릴 수 있으므로 다음 순서로 한다.

1. 웹: 새 필드가 없어도 동작하게 배포(없으면 기본 규격·제철 링크 없음).
2. 배치: 새 필드를 쓰는 판정 묶음 생성.
3. 웹: 새 필드를 쓰는 화면 배포.
4. 옛 형식 처리 코드 정리.

필드를 지우거나 뜻을 바꾸는 변경은 이 순서를 거꾸로 한다. ADR 0004에 이 절차를 추가한다.

## 캐시와 지연

- 공개 지연 허용치: 다음 판정 배치까지(하루 이내) + 웹 목록 캐시 시간. 운영자 1명이라 이 이상 줄일 필요가 없다.
- 급한 정정(잘못된 가격 노출): 코드 수정 → 적용 → `judgment`를 손으로 실행 → 필요하면 웹 캐시 무효화. 무효화 방법(`revalidateTag` 등)이 지금 있는지 구현 전에 확인하고, 없으면 "다음 캐시 만료까지 남는다"를 받아들일지 정한다.

## 실패와 복구

| 상황                                         | 공개 화면                 | 할 일                                                                                                                                    |
| -------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 판정 배치 실패·검사 실패                     | 직전 묶음 유지(현재 동작) | 경보 확인, 원인 수정 후 재실행                                                                                                           |
| 카탈로그 적용(`--classes`·`--mappings`) 실패 | 직전 묶음 유지            | 트랜잭션이라 되돌아간다. 수정 후 재적용                                                                                                  |
| 잘못된 카탈로그가 공개됨                     | 잘못된 묶음               | `git revert` → 재적용 → `judgment` 재실행. 포인터만 직전 묶음으로 되돌리는 명령이 있으면 그것이 더 빠르다(있는지 확인, 없으면 추가 검토) |
| 웹 배포가 payload를 못 읽음                  | 목록 누락·상세 오류       | 웹 이전 배포로 되돌림. 위 배포 순서가 이를 막는다                                                                                        |

포인터를 되돌려도 다시 매핑된 관측값·일자 요약은 되돌아가지 않는다. 그래서 잘못된 매핑은 포인터가 아니라 `git revert` + 재적용으로 고친다.

## 백업 (지금 할 일)

카탈로그 매핑 대부분은 코드로 다시 만들 수 있지만, 다음은 코드에 없다: 운영자가 코드와 다르게 정한 매핑, `store_seller`, `store_link`, `calc_param`, `market.type_source` 등(`pipeline.md` 7장 목록). 지금은 백업이 없다.

- `pipeline.md`가 계획한 대로 주 1회 `pg_dump --schema=price`를 GitHub Actions 아티팩트로 남긴다. 기존 월요일 보존 정리 워크플로 뒤에 붙인다.
- 한 번은 로컬 DB에 복원해 본다(`pnpm db:reset` 후 `pg_restore`).
- 자격증명은 기존 Secrets를 쓰고, 덤프에 비밀이 들어가지 않는지 확인한다.

## 하지 않는 것

카탈로그 공개 버전 표, 편집본·공개본 분리, 긴급 숨김 전용 경로, 범용 버전 프레임워크.

## 완료 기준

- 01·04의 새 필드가 위 배포 순서로 나가고, 두 조합(옛 payload + 새 웹, 새 payload + 옛 웹)에서 목록이 비지 않는다.
- 주간 백업이 돌고, 복원 연습 결과가 기록돼 있다.
- 잘못된 매핑 하나를 `git revert`로 되돌리는 연습을 로컬 DB에서 한 번 해 본다.

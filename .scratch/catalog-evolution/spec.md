## 목적

수집된 가격을 품종 × 규격별로 찾게 하고, 미연결 원천 데이터를 빠짐없이 검토하며, 제철 품종과 시세를 명시적인 대응으로 잇는다. 카탈로그 변경이나 재계산이 실패해도 공개 화면은 직전 정상 판정을 보여 준다.

카탈로그는 카테고리·품목·품종·규격·별칭·원천 매핑·제철 매핑을 함께 가리킨다. 용어는 `grocery-price/GLOSSARY.md`를 따른다.

## 전제: 운영자는 1명이다

운영자는 개발자 본인 1명이다. 이 전제에서 다음을 정한다.

- **카탈로그 원본은 코드(`packages/price-ingest/src/catalog/varieties.ts`, `match.ts`)로 유지한다.** git 기록이 감사 기록·변경 전후 비교·롤백을 맡는다. DB를 원본으로 바꾸지 않는다.
- **운영 어드민(쓰기 화면)은 만들지 않는다.** 인증·인가·CSRF·역할·동시 편집 충돌 처리가 필요 없다. 검토는 읽기 전용 CLI 보고서로 한다(05).
- **공개는 기존 판정 묶음 + 현재 포인터(`judgment_current`) 교체로 한다.** 별도 카탈로그 공개 버전 체계를 만들지 않는다(06).
- 운영 DB의 카탈로그 표를 손으로 고치지 않는다. 고쳐도 다음 `catalog --classes`가 코드대로 되돌린다.

### 이 전제를 다시 볼 조건

다음 중 하나가 생기면 DB 원본 전환과 어드민 쓰기 화면을 다시 검토한다. 처음 작성한 DB 원본안의 요지와 기각 이유는 [검토 기록](review.md) "기각한 안"에 남긴다.

- 코드를 고치지 않는 운영자가 생긴다.
- 카탈로그 변경이 잦아 커밋 → 적용 → 재계산 흐름이 병목이 된다(예: 주 10건 이상이 몇 주 이어짐).
- 원천 연결 판단에 개발 환경 없이 즉시 대응해야 하는 일이 반복된다.

## 확인된 현재 구조

1. `variety-list.md` 규칙 3·4: 원산지는 품종, 보관 상태·크기·등급은 규격이다.
2. `catalog/varieties.ts`가 원본이고 `catalog/cli.ts`가 DB에 반영한다. `--classes`(소유자 접속)는 분류 표를 맞추고 코드에 없는 품종을 `hidden`으로 바꾼다. `--mappings`(`ingest_writer`)는 매핑을 넣고, 쌓인 관측값을 다시 매핑하고, 일자 요약을 다시 계산한다. 운영자가 코드와 다르게 정한 매핑은 고치지 않고 알린다.
3. 적재(`loadRawFile()`)는 처음 본 키를 카탈로그대로 잇고, 카탈로그에 없으면 pending으로 남긴다. 새 공개 품종을 스스로 만들지 않는다.
4. `judgment/cli.ts`는 `spec.is_default`로 조인한다(57·66·80행). 평소가 조회(75행)는 `variety_id`만 키로 쓴다. 지금은 품종마다 기본 규격 하나만 판정한다.
5. 웹 `queries/get-variety.ts`는 `payload ->> 'id' = 품종 slug`로 `limit 1` 조회한다.
6. `price.variety_seasonal_map`은 다대다를 지원하지만 웹 `priceVarietyPath()`는 같은 ID 문자열만 비교한다.
7. 관측값 보존: KAMIS 90일, 참가격 최근 6 조사일, 축평원 영구(그날 요약이 있을 때만 지움). KAMIS 원본 파일은 1년 보관(`pipeline.md` 3-9). 원본에서 표본을 다시 만드는 경로는 재등록 처리용으로만 설계돼 있고, 매핑 변경용 일반 재계산은 없다.
8. 운영 매핑의 `pg_dump` 백업은 아직 없다(`pipeline.md` 7장, "정식 서비스 전으로 미룸").

## 원칙

- 검색에서 묶는 것과 시세 계산에서 합치는 것은 별개다.
- 가격 비교·판정은 품종 × 규격 단위로 한다. 원천 데이터가 없는 조합은 만들지 않는다.
- pending 0건을 목표로 삼지 않는다. 근거 없는 연결은 보류한다.
- 공개 화면은 판정 묶음 포인터가 가리키는 한 벌만 본다.

## 진행 순서

1. **준비:** 출처별 pending 재조회, 운영 DB `price` 스키마 `pg_dump` 주간 백업 추가(06). 백업은 카탈로그 작업과 상관없이 먼저 한다.
2. **01 규격별 판정·검색:** 꽃게·시금치로 검증 후 규격 200개 전체로 공개. 다른 계획을 기다리지 않는다.
3. **03 + 05:** pending 보고서 CLI → 코드 카탈로그 수정 → 적용 흐름을 정리하고, 최근에 관측된 pending부터 처리.
4. **04:** 제철 링크를 명시 매핑으로 전환하고 누락 검사 테스트 추가.

각 단계는 하나의 구현 티켓(`.scratch/catalog-evolution/issues/`)으로 쪼갠다. 계획 확인 전에는 `ready-for-agent` 티켓을 만들지 않는다.

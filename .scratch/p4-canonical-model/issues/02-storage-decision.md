# 02. 저장소 결정

Status: ready-for-human
Type: grilling
Blocked by: 01

## 목적

통합 데이터와 원본(raw)을 **어디에 저장하고 어떻게 읽을지** 정한다. 로드맵 P6의 일부를 앞당긴 결정이다. 정식 확정은 P6에서 호스팅·배치와 함께 하고, 여기서는 스키마가 의존할 수 있는 방향을 정한다.

## 입력 사실

- 데이터 규모는 크지 않다. 추정할 항목: 품종 수 × 출처 × 일수. KAMIS 호출 한도와 품종 수로 일일 증가량을 계산한다.
- 쓰기는 하루 몇 번의 배치뿐이고, 읽기는 사용자 요청이다.
- 참조 사례: 다른 프로젝트는 GitHub Actions 배치 + JSON 게시 + GitHub Pages로 앱이 API를 직접 부르지 않게 했다 (api-spec.md 4장). 이유: 개발계정 한도와 인증키 노출.
- 판정에 필요한 질의: 품종별 최근 N주 중앙값, 같은 달 예년 가격, 최저·최고. 이 질의가 쉬운지가 선택 기준이다.
- SEO 대상 페이지 수에 따라 렌더링 방식이 달라진다 (P9 → P6 입력).

## 선택지 (예시, 에이전트가 사실 확인 후 정리)

| 선택지 | 장점 | 단점 |
|---|---|---|
| 관계형 DB (Postgres 등) | 기간 집계·조인 쉬움, 정정 이력 관리 | 운영 비용 |
| SQLite 파일 | 단순, 비용 없음 | 배포·동시 쓰기 제약 |
| 정적 JSON/Parquet 파일 + 배치 | 비용 낮음, 키 노출 없음 | 질의 유연성 낮음 |

## 결정할 것

- [ ] raw와 정규화 데이터의 저장 위치를 같이 둘지 분리할지
- [ ] 판정에 필요한 질의를 이 저장소에서 어떻게 계산할지
- [ ] 월 비용 상한
- [ ] 백업·재구축: raw에서 정규화를 다시 만들 수 있는지

## 완료 기준

- 선택과 이유가 ADR(`grocery-price/docs/adr/0002-...`)로 기록되어 있다. 필요하면 P6에서 재검토한다고 명시한다.
- 통합 스키마(01)가 이 선택으로 깨지는 부분이 없는지 확인했다.

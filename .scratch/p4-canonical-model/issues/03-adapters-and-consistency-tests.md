# 03. 어댑터 구현과 일관성 테스트

Status: resolved
Type: task
Blocked by: 01, p2-data-source-spec/12

## 목적

각 출처의 응답을 통합 스키마(01)로 바꾸는 어댑터를 만들고, **세 출처의 결과가 같은 규칙을 지키는지** 테스트한다. `p2/12`가 "출처가 이전과 같은가"를 보증한다면, 이 이슈는 "우리 쪽 변환이 일관적인가"를 보증한다.

산출물: 수집 패키지(`ingest-foundation/03`, `packages/price-ingest` 제안) 안의 어댑터 코드와 테스트. 변환 예시표는 테스트 픽스처와 pipeline.md에 둔다.

## 할 일

- [x] 출처별 어댑터: 출처 응답(검증된 형태) → 가격 관측 레코드
  - 숫자 문자열 → 숫자 변환, 빈 값 → `null`
  - 단위 환산 (KAMIS kg 환산가, 축평원 원/100g, 참가격 용량·단위)
  - 원천 코드 → 품종·규격 매핑 (매핑표는 `p3-variety-catalog/01` 결과. 없으면 "미매핑"으로 두고 건수 보고)
  - 참가격 행사 플래그 → 행사 필드
- [x] 일관성 테스트 (세 출처 공통)
  - 출력이 스키마를 만족한다 (필수 필드, 타입, 값 범위)
  - 같은 입력을 두 번 변환하면 같은 결과다 (결정성)
  - 동일 출처 원본 키는 재수집해도 중복 레코드를 만들지 않는다
  - 단위 환산 결과가 알려진 샘플과 일치한다 (예: KAMIS 배추 1포기, 축평원 삼겹살 100g)
  - 가격이 0이거나 음수이거나 비정상적으로 큰 값이면 이상치로 표시된다
- [x] 미매핑 건수 리포트: 출처 코드 중 어떤 품종에도 연결되지 않은 것 목록
- [x] 변환 불가 케이스(01의 목록)마다 의도한 동작을 테스트로 고정
- [ ] 변환 결과를 Postgres에 쓰는 부분은 `ingest-foundation/03`에서 구현한다.

## 완료 기준

- 3개 출처 샘플 모두 통합 스키마로 변환되고 일관성 테스트가 통과한다.
- 출처별 변환 예시가 테스트 픽스처로 있다.
- 샘플 필드를 일부러 깨뜨리면 어느 단계(계약 테스트 vs 변환 테스트)에서 잡히는지 확인했다.

## Answer

2026-10-22. `packages/price-ingest/src/adapt/`에 만들었다. 결과는 DB 번호가 아니라 원천 키와 장소 키를 담은 **관측값 초안**이다. 번호로 바꾸는 일은 적재 트랜잭션이 한다 (`ingest-foundation/03`, 결정 B).

- **어댑터**: `kamis.ts`(`adaptKamisRow`), `ekape.ts`(`adaptEkapeRow`, 평년 행은 `reference` 초안), `chamga.ts`(`adaptChamgaPriceRow`). pipeline 3-11 표의 열마다 한 함수.
- **단위 환산** (`units.ts`): pipeline 3-1 계산식 `원천 가격 ÷ (원천 수량을 기준 단위로 바꾼 값) × base_unit_qty`. 같은 단위끼리, 무게↔개수는 `g_per_ea` 기준이 있을 때만 한다. 구(계란 30구)는 개(ea)와 같은 개수로 본다. 결과는 소수 둘째 자리까지 반올림한다.
- **매핑은 함수로 받는다** (`mapping.ts`): 실제 품종 목록(p3/01)과 `source_code_map`은 아직 없다. 테스트는 임시 매핑 픽스처(`test/fixtures/adapt.ts`)를 쓴다. 매핑이 없으면 품종·규격과 기준 단위 가격을 비우고, `unmappedReport`가 원천 키별 건수를 낸다.
- **일관성 테스트** (세 출처 샘플 배치): 스키마 만족, 같은 입력은 같은 결과, 배치 안에서 자연키 중복 없음, 같은 배치를 다시 합쳐도 행 수 불변.
- **3-12 변환 불가 26개**: 케이스마다 테스트에 `(3-12 #n)`을 붙였다. 어댑터가 정하는 것은 값을 검사하고, 어댑터 밖(DB·적재·②)이 정하는 것(#6 시장 유형, #17, #18, #19, #20, #25 등)은 원천 값이 그대로 넘어가는지만 검사한다. 처음 기록에는 26개 모두라고 적었으나 #6이 빠져 있었다 (2026-10-22 점검에서 더함, 아래 Comments).
- **이상치**: **임시 상한 1천만 원**을 넘으면 `outlier`. 상한은 pipeline에 없는 숫자라서 ②에서 다시 정한다. 전날·다른 시장과 비교하는 규칙(pipeline 5-2)은 ②·③ 몫이다. 가격 0 이하는 이상치가 아니라 행 단위 거부다 (아래 Comments).
- **1+1**: 1개 값인지 묶음 값인지 모르므로 기준 단위 가격을 비우고 `one_plus_one_unverified`를 붙인다 (#13).
- **참가격 상품 용량**: 가격 행에는 없어서 상품 정보(`goodTotalCnt`, `goodTotalDivCode`)를 함수로 받는다. 상품 정보가 없으면 기준 단위 가격은 null이다.
- **검증 결과**: 오프라인 테스트 135개 통과 (이번에 67개 추가). 타입 검사와 린트 0 오류.
- **샘플 깨뜨림 확인**: `kamis/vegetable-baechu-retail.json`의 `exmn_dd_prc`를 바꾸자 계약 단계(`parseKamisPerDay`)에서 잡혔다. 같은 샘플을 쓰는 변환 테스트 20여 개도 같은 원인으로 실패했다. 샘플은 되돌렸다.

**기본값으로 정한 것** (ingest-foundation 03의 3~5번, 확인 전까지 권장안으로 둔다): `recompute` 계산식은 시제품 `fixture-1`을 그대로 두고 배선만 만든다. `price-db`의 시제품 로더와 정식 로더는 정식 쪽을 가져다 쓰게 한다. `merge-product`는 03 범위에 넣는다.

## Comments

- 2026-10-22 점검 뒤 고침:
  - **행 단위 거부** (pipeline 3-11): 처음에는 가격 0 이하를 `outlier`로 표시만 했다. 그런 행이 하나만 있어도 DB 검사 `price_raw > 0`이 원본 파일 하나의 적재 전체를 되돌린다. 그래서 `kamisRowRejection`, `ekapeRowRejection`, `chamgaPriceRowRejection`이 거부 사유를 내고, `adaptRows`(`src/adapt/batch.ts`)가 거부된 행을 몇 번째 행인지와 사유와 함께 따로 모은다 (`raw_object.rejected_rows`). 어댑터를 바로 부르면 `RowRejectedError`를 낸다. KAMIS는 가격·단위 크기·구분 코드·요청 기간·축산 밖의 null을, 축평원은 가격·요청 축종을, 참가격은 가격을 본다.
  - **3-12 #6** 테스트를 더했다: 이름 규칙으로 못 가르는 시장(`1000006` `가락소매`)도 시장 코드로 장소를 잡고, 시장 유형은 어댑터가 정하지 않는다.
  - **어댑터 버전** `ADAPTER_VERSION`(`2026-10-22.1`)을 둔다. `raw_object.adapter_version`에 들어간다. 변환 규칙을 바꾸면 올린다.
  - 아직 없는 것: 초안에는 시장 이름·지역 코드, 점포 정보가 없다. 적재가 `obs_place`·`market`·`store` 행을 만들 때 원본 행이나 마스터에서 읽어야 한다 (`ingest-foundation/03` 2차).

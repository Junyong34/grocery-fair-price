테이블 연결 관계

40개를 한 그림에 넣으면 읽을 수 없어서 역할별 6개 묶음으로 나눴습니다. 각 그림에는 키와 연결에 필요한 열만 넣었습니다. 전체 열은 pipeline.md 3장에 있습니다. 부모 쪽 |o는 FK 열이 비어 있을 수 있는(null 허용) 연결, 점선은 FK가 없는 논리 연결입니다. 품종·규격은 (variety_id, spec_id) 복합 FK로 spec을 가리키므로 3~5 묶음에는 spec을 그렸습니다.

1. 분류와 원천 코드

  • 품종이 중심입니다. 카테고리 → 품목 → 품종 → 규격 순으로 내려갑니다.
  • 출처의 코드 조합 하나가 source_item 한 행입니다.
  • source_code_map이 원천 키를 품종·규격에 잇습니다. 기간이 겹치면 DB가 거부합니다.
  • 품종과 규격은 (variety_id, spec_id) 복합 FK로 함께 잇습니다. 다른 품종의 규격은 들어가지 않습니다.
  • 가격 품종과 제철달력 품종은 variety_seasonal_map으로만 이어집니다.

2. 위치: 점포, 조사 시장, 지역

  • obs_place는 가격이 관측된 곳입니다. 점포, 조사 시장, 지역 평균 중 하나입니다.
  • 점포는 store_seller로 기간별 판매처에 이어집니다. 과거 평균은 당시 판매처로 계산됩니다.
  • 재등록된 점포는 store_link와 lineage_id로 옛 점포와 이어집니다.
  • 출처마다 다른 지역 코드는 region_code_map이 법정동 코드로 바꿉니다.
  • 범위(scope)와 지역은 위치마다 고정이라 관측값이 아니라 obs_place에 한 번만 둡니다. store·market은 상수 kind로 위치 종류가 맞는지 DB가 확인합니다.

3. 관측값

  • 키는 (원천 키, 조사일, 관측 위치)입니다. 같은 행을 다시 받으면 비교해서 값이 바뀐 행만 고쳐 씁니다.
  • 출처·범위·지역은 조인으로 얻으므로 관측값 행에 두지 않습니다. 행당 약 200~250B로 봅니다.
  • 값이 바뀌면 observation_revision에 이전 값을 남기고 revision을 올립니다. 이력은 관측값이 지워져도 남도록 FK 없이 키만 들고 있습니다 (점선).
  • 보존 기간이 지난 날짜가 다시 등록되어 오면 관측값에 넣지 않고, 원본 파일 전체로 그날 표본을 복원해 집계를 바꿉니다. 원본이 불완전하면 집계를 그대로 둡니다.
  • 축평원 평년 행은 관측값이 아니라 reference_observation에 들어갑니다.
  • 모든 행은 자기를 만든 원본 파일(raw_object)을 가리킵니다.

4. 상품 (참가격)

  • 참가격 상품 번호 대신 우리 상품 ID를 씁니다. 재사용하거나 지우지 않습니다.
  • product_source_key가 출처 번호를 기간별로 상품에 잇습니다. 110g과 120g은 다른 상품입니다.
  • 이름·용량이 바뀌면 product_attr_history에 새 기간이 생깁니다.
  • 상품은 소분류 규칙(al_variety_rule)으로 품종에 묶고, 예외만 손으로 고칩니다.
  • 같은 물건인 두 상품은 운영자 작업으로 병합합니다. 옛 상품은 merged 상태로 남고 merged_into를 따라 새 상품을 보여 줍니다.
  • 등록일(registered_on)과 처음 가격이 관측된 날(first_price_on)을 따로 둡니다.

6. 수집 상태와 원본

  • GitHub Actions 한 번 실행이 ingest_run 한 행입니다. 호출 수와 예산을 함께 남깁니다.
  • source_day는 출처 × 날짜별 상태입니다: 대기, 정상, 일부, 휴일, 예상 밖 빈 날, 실패. 받은 뒤 값이 바뀐 것은 상태가 아니라 corrected_at·correction_count로 남깁니다.
  • source_day_part는 품목·판매처 단위의 누락을 잡습니다.
  • 원본 파일은 내용 해시가 같으면 다시 올리지 않고 duplicate로 기록합니다.
  • 보존 기간이 지난 원본은 Storage 파일만 지우고 raw_object 행은 purged_at을 채워 남깁니다. 관측값이 이 행을 가리키기 때문입니다.

보관과 용량

무엇을 얼마나 오래 두는가

데이터DB에 두는 기간용량 (추정)그 뒤에는
KAMIS 시장별 관측값최근 90일약 70~85MB시장 유형별·품종별 집계로 영구. 시장 하나의 추이는 90일까지. 5년 백필은 세션 임시 표를 거쳐 집계와 최근 90일만 남김
참가격 점포별 관측값최근 8 조사일 (약 16주)약 130~225MB상품별 집계로 영구
축평원 관측값·평년영구약 15~18MB (5년)-
집계 (daily_quote 등)영구약 90~110MB (5년) + 연 50~60MB (평년·상품 집계 포함)-
평소가 (usual_price)영구연 약 8만 행, 약 16~24MB화면에 필요한 날짜만 두면 줄어듦
원본 파일Storage1년차 250~330MB, 이후 연 130~200MBKAMIS·축평원은 1년 뒤 파일 삭제(기록 행은 남김), 참가격은 영구
DB 합계 (1년차)약 365~515MB이후 연 70~95MB 증가. 상단은 무료 500MB를 넘음

행당 크기를 어림한 값입니다 (2026-10-20에 관측값 200~250B, 집계 120~150B로 올림). 마이그레이션 단계에서 관측값 1만 행과 집계 표 샘플을 넣어 pg_total_relation_size로 먼저 잽니다.

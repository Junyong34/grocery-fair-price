# 카탈로그 원본은 코드가 아니라 DB 표다

카테고리·품목·품종·규격·상품의 분류와 원천 코드 매핑은 운영 DB의 `price` 표가 원본이다. 바꾸는 길은 로컬 전용 카탈로그 어드민(`pnpm dev`, 소유자 접속)의 승인 하나다. 처음에는 `packages/price-ingest/src/catalog/varieties.ts`·`match.ts`가 원본이었고 `catalog --classes`가 DB를 그 코드대로 맞췄다. 2026-11-09에 바꿨다 (`.scratch/catalog-scale/spec.md`).

이유: 항목을 품종 136개에서 가공식품 상품을 포함한 수천 개로 늘린다. 그 규모에서는 로컬 에이전트가 미연결 원천 키에 분류 제안을 쓰고 사람이 여러 건을 한꺼번에 승인한다. 코드가 원본이면 승인마다 코드 수정 → 커밋 → 적용 → 재계산을 거쳐야 하고, 수천 줄짜리 TS 파일의 리뷰와 충돌이 병목이 된다. 11-05 계획(코드 원본 유지)이 스스로 적어 둔 재검토 조건("카탈로그 변경이 잦아 커밋 → 적용 흐름이 병목")에 해당한다.

## 고려한 대안

- **코드 원본 유지, AI가 TS를 고친다**: git 기록이 감사 기록·되돌리기를 공짜로 준다. 하지만 수천 개 규모의 diff는 사람이 읽기 어렵고, 승인이 배포에 묶인다.
- **저장소의 데이터 파일(JSON)을 원본으로**: 코드보다 다루기 쉽지만, 승인 화면이 결국 파일을 고치고 커밋하는 도구가 되어 DB 원본과 같은 어드민이 필요하다.

## 결과

- 운영자가 승인한 분류는 원천 데이터로 다시 만들 수 없다. 그래서 승인할 때마다 카탈로그 표를 저장소에 JSON으로 내보내 커밋한다. 이 내보낸 파일이 백업이고 로컬 DB를 채우는 입력이다. Supabase는 Free 플랜이라 자동 백업이 없다. Pro로 바꾸면 일일 백업이 더해진다.
- 변경 기록(누가·언제·무엇을·전후 값)은 DB의 변경 기록 표가 맡는다. git 기록이 하던 일이다.
- 어드민은 배포하지 않는다. 배포된 웹은 계속 `web_reader`로 공개 판정만 읽는다 (ADR 0002). 그래서 로그인·권한·CSRF를 만들지 않는다.
- `varieties.ts`는 DB로 한 번 옮긴 뒤 원본에서 내린다. `catalog --classes`가 DB를 코드대로 되돌리는 동작은 없앤다.

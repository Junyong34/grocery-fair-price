# 로드맵

서비스는 네 단계로 만든다. 데이터를 모으고(1), 그 데이터로 판정하는 규칙을 정하고(2), 화면 콘텐츠를 설계한 뒤(3), 이미 있는 Next.js 앱 `apps/web`에 화면을 만든다(4). 앞 단계에서 정한 내용이 뒤에서 틀린 것으로 드러나면 해당 문서를 고치고 변경 사유를 남긴다.

1순위는 하나다. 사용자가 삼겹살, 배추, 당근을 사려고 할 때 **그 가격이 싼지, 보통인지, 비싼지** 바로 보여 준다. 나머지 기능은 출시 뒤에 계속 더한다.

## 전체 흐름

```
P0 기획·조사 ✅ ── P1 도메인 모델링 ✅
 │
 ├─ ① 수집 기반     API 3개 요청·응답 분석 → 스키마 → Supabase 적재 → GitHub Actions 정기 수집 → 장애 처리
 ├─ ② 판정 설계     평소가·판정 계산식, 품종 목록, 점포 데이터가 없는 품종의 대체 콘텐츠
 ├─ ③ 화면 설계     검색 결과(판정 → 시세·추세 → 업태별 가격), 차트, 화면 구성안
 └─ ④ 구현          apps/web에 가격 화면 추가, SEO 등록, 배포
```

- **수집 코드는 ①에서 바로 만든다.** 스키마가 정해지면 수집과 적재를 시작한다. 참가격은 2026-06-12 이전을 주지 않으므로 늦게 시작할수록 이력을 잃는다.
- **화면 코드는 ④에서만 쓴다.** ②③의 설계가 끝난 뒤 시작한다.
- ②의 품종 목록은 ①의 품목 전수 목록(p2/13)이 나오면 ①과 겹쳐 시작할 수 있다.

## 단계별 정의

### P0. 기획·조사 ✅

- 산출물: `docs/10-research/` (공공데이터 조사, 법적 검토, 이미지, 분류 체계), [ADR 0001](../adr/0001-public-data-and-reports-over-crawling.md)

### P1. 도메인 모델링 ✅ (2026-10-08)

- 산출물: `GLOSSARY.md`, [domain-model.md](../20-domain/domain-model.md)
- 이후 모든 단계가 이 용어를 쓴다. 새 용어가 필요하면 용어집부터 고친다.

### ① 수집 기반

- **목표**: 공공 API 3개의 데이터를 Supabase에 매일 쌓고, 장애가 나도 서비스가 마지막 정상 데이터로 계속 돌게 한다.
- **출처** (data.go.kr 개발계정, 키는 `.env`의 `DATA_GO_KR_SERVICE_KEY` 하나)
  - 한국농수산식품유통공사 일별 도·소매 가격정보 (KAMIS `perDay/price`)
  - 축산물품질평가원 축산물유통정보 (소비자가격)
  - 한국소비자원 생필품 가격 정보 GW (참가격, data.go.kr 15158701)
- **선행 작업 (사용자)**: Supabase 계정·프로젝트 생성, 연결 정보를 `.env`와 GitHub Actions Secrets에 등록 (`ingest-foundation/01`)
- **산출물**
  - 요청·응답 실측: [api-spec.md](../10-research/api-spec.md), 응답 샘플 `reference/public-data/samples/`
  - 파이프라인 설계: [pipeline.md](../30-data/pipeline.md) (저장 구조, 테이블, 수집 일정, 장애 처리)
  - 실행 환경 결정: [ADR 0002](../adr/0002-supabase-and-github-actions.md)
  - Postgres 스키마·마이그레이션·롤·권한 (`supabase/migrations/`). 표는 노출하지 않는 스키마 `price`, 수집은 `ingest_writer` 롤, 웹앱은 `web_reader` 롤로 서버에서만 읽는다 (2026-10-20, [pipeline.md](../30-data/pipeline.md) 3-0)
  - 수집 패키지(API 클라이언트, 계약 테스트, 변환, 적재)와 GitHub Actions 워크플로
  - KAMIS 5년 이력 백필 (평년 계산 입력)
- **완료 기준**
  - 세 출처가 정한 시각에 사람 손 없이 수집·적재된다.
  - 세 출처의 모든 응답 필드가 도메인 개념에 연결되거나 "미사용"이다.
  - [pipeline.md](../30-data/pipeline.md) 5장의 장애 상황마다 감지·보정·알림이 동작하고, 수집이 실패해도 화면이 읽는 집계는 마지막 정상 값을 유지한다.
- 작업: `.scratch/ingest-foundation/`, `.scratch/p2-data-source-spec/`, `.scratch/p4-canonical-model/`

### ② 판정 설계

- **목표**: 수집한 데이터로 평소가와 판정을 계산하는 규칙과, 판정할 품종 목록을 정한다.
- **산출물**: `docs/30-data/judgment.md`, `docs/30-data/variety-list.md`
  - 평소가 계산식: KAMIS 5년 이력으로 계산한 평년, 축평원 평년, 최근 N주 중앙값을 섞는 방식
  - 판정 구간(싸다·보통·비싸다)과 품종별 변동성 반영, 신뢰도
  - 품종 목록: 카테고리별 품종과 출처 코드. 가격 품종 ID는 제철 패키지와 별도 체계로 두고 매핑표로 잇는다
  - 상품→품종 매핑(참가격 소분류 단위), 점포→판매처 매핑
  - 점포 데이터가 없는 품종(배추·당근 등)에 보여 줄 대체 콘텐츠: KAMIS 전통시장 대 대형유통, 축평원 시도별 가격, 평년 비교, 제철 정보
- **완료 기준**
  - MVP 품종마다 시세를 주는 출처가 하나 이상 있다.
  - 모든 판정값이 ①의 테이블만으로 계산되고, 데이터가 부족할 때의 동작이 정해져 있다.
- 작업: `.scratch/p3-variety-catalog/`, `.scratch/search-first-view/05`

### ③ 화면 콘텐츠 설계

- **목표**: 검색 한 번에 판정이 보이는 화면을 설계한다.
- **산출물**: 화면 구성안(375·1280 와이어프레임)과 콘텐츠 블록
  - 검색 결과: 판정 → 오늘 시세·최근 추세 → 업태별(대형마트, 백화점, 슈퍼, 편의점, 전통시장) 가격 추이
  - 차트: 품종은 시세 선 + 평소가 띠, 상품은 평균 선 + 최저~최고 띠
  - 점포 데이터가 없는 품종의 화면
  - 판정 3색과 차트 색 토큰 (색 + 아이콘 + 문구로 함께 표시, 명도 대비 통과)
- **완료 기준**: 1순위 화면(품종 판정)의 구성안이 승인되고, 블록마다 읽는 테이블이 정해져 있다.
- 작업: `.scratch/search-first-view/`

### ④ 구현

- **목표**: `apps/web`에 가격 화면을 만들고 배포한다.
- **할 일**
  - `packages/ui`에 판정·차트 색 토큰 추가 (Oura 팔레트 안에서, 라이트 모드 전용)
  - 웹앱이 DB를 읽는 경로: 접속은 정해졌다(서버 컴포넌트 + `web_reader`, `WEB_DATABASE_URL`). 캐시 단위와 갱신 신호는 여기서 정한다 (`ingest-foundation/06`)
  - 가격 페이지를 `apps/web/shared/seo/pages.ts`에 등록, 메타데이터는 `createMetadata`
  - `/` 가격 메인으로 교체 (`app/page.tsx`의 리다이렉트를 대체, 제철 경로는 그대로)
- **선행 작업 (사용자)**: 운영계정 전환 신청(개발계정 활용기간 만료 전), 도메인, Search Console
- **정식 서비스 전에 할 것**: DB 백업 시작. 주 1회 `pg_dump`(Actions 아티팩트로 최근분, 달마다 한 벌을 비공개 Storage 버킷에). 시제품 단계라 미뤘다 (2026-10-20). 운영자가 정한 매핑은 원본으로 되살릴 수 없으므로 출시 전에 꼭 켠다 ([pipeline.md](../30-data/pipeline.md) 6-1)
- **완료 기준**: 운영 배포, 375·1280 폭에서 콘솔 오류 없음, sitemap 제출

## 이전 단계와의 대응 (2026-10-19 재편)

처음 로드맵은 P0~P11 열두 단계였고, 단계마다 완료 기준을 다 채워야 넘어가며 코드는 P11에서 시작했다. 2026-10-19에 아래 이유로 네 단계로 다시 짰다.
- 앱(`apps/web`, Next.js 16, Vercel)과 디자인 시스템(`packages/ui`, Oura), SEO 체계(`shared/seo`)가 제철달력으로 이미 있다. 이를 다시 설계하는 단계(P6 프런트엔드·호스팅, P7, P9, P10)는 티켓 몇 개로 줄었다.
- 참가격 과거 조회가 2026-06-12부터만 되므로 수집을 미룰수록 이력을 잃는다. 수집 코드를 설계 단계 뒤로 둘 수 없다.
- 저장소와 배치는 Supabase + GitHub Actions로 정했다 ([ADR 0002](../adr/0002-supabase-and-github-actions.md)).

| 이전 | 지금 |
|---|---|
| P2 데이터 소스 명세 | ① 요청·응답 분석 (`p2-data-source-spec`) |
| P3 표현 가능 값 카탈로그 | ② 품종 목록 |
| P4 어댑터 · 통합 데이터 모델 | ① 스키마·변환 |
| P5 표현 설계 (지표 · 위젯) | ② 계산식, ③ 화면 블록 |
| P6 기술 아키텍처 | ADR 0002 |
| P7 디자인 시스템 | ③④ 판정·차트 색 토큰 한 장 |
| P8 정보구조 · 페이지 설계 | ③ |
| P9 SEO · 분석 설계 | ④ 가격 페이지 등록 (`.scratch/seo` 체계 사용) |
| P10 디자인 시안 | ③ 와이어프레임 + 개발 서버 확인 |
| P11 구현 · 배포 · 등록 | ④ |

`.scratch/p2-*`, `p3-*`, `p4-*` 폴더 이름은 이전 번호를 그대로 쓴다.

## 확장 단계 (MVP 출시 이후)

1차 데이터셋은 공공데이터로 만든다. 아래는 출시 뒤 하나씩 더한다.

### E1. 온라인몰 데이터

- **목표**: 온라인몰 판매가를 합법적으로 가져올 방식과 수집 주기를 정한다.
- **검토할 것**
  - 확보 방식: 제휴·상품 피드, 공식 API의 실시간 표시, 제한적 수집 (각각의 법적 검토는 [data-sourcing-legal.md](../10-research/data-sourcing-legal.md))
  - 수집 주기: 품종별 가격 변동성과 온라인몰의 가격 변경 빈도를 근거로 정한다
  - 배송비, 멤버십 가격, 최소 주문 금액을 판매가에 반영하는 규칙
- **완료 기준**: 온라인몰별 확보 방식·주기가 ADR로 기록되고, 변환 규칙이 추가됨

### E2. 사용자 제보

- 사용자가 본 판매가를 입력하고, 검수를 거쳐 공개한다 ([domain-model.md](../20-domain/domain-model.md) 5장). 로그인과 검수 운영이 필요해 MVP에서 뺐다 (2026-10-19).

### E3. 도매 시세와 예고 문구

- "도매 가격이 2주째 올라 소매도 오를 수 있어요" 같은 예고. 출처 후보는 `.scratch/search-first-view/07`.

### E4. 가격 이슈 (보조 출처)

- 기상 특보, 가축 질병, 뉴스 키워드로 가격 이슈를 알린다. 조사 티켓은 `p2-data-source-spec/08~10`.

### E5. 공개 API

- 외부용 `/api/v1`. MVP 화면은 서버 컴포넌트가 DB를 직접 읽고, 직접 입력한 가격의 판정은 클라이언트에서 계산한다.
